## 1. Проблема і вимоги власника

Сьогодні фінансова модель «висить» на двох незвʼязаних механіках: разові `Order`
(fixed/hourly) і recurring-підписки `Service → CompanyService → ServiceCharge`.
Обидві — на рівні **компанії цілком**: одна валюта (`Company.currency`), без
договору, без власного білінг-циклу, без розрізу маржі.

Вимога власника (дослівно за змістом, із проходу 11.06.2026):

> Відносно ОДНОГО клієнта може бути ДЕКІЛЬКА паралельних фінансових моделей —
> «проєктів»/інстансів, кожен зі своїми договором, рахунками, валютою і правилами.
>
> - Приклад: (1) «Оренда» — щомісячне фіксоване АВАНСОВЕ нарахування, свій
>   договір/рахунки; (2) «Програмування» — чисто погодинні роботи, своя ставка;
>   (3) інші послуги — інша ставка/абонплата, інший договір.
> - **Абонплати — ЗАВЖДИ авансові. Погодинні — авансові АБО по факту** (налаштування моделі).
> - Різні проєкти одного клієнта — можуть бути в РІЗНИХ валютах.
> - Договір: для якихось типів обовʼязковий, для якихось опційний — продумати обовʼязковість полів.
> - **Маржа per-проєкт/per-виконавець**: клієнт платить **$30/год** по проєкту →
>   програміст отримує **$10/год** → агенція лишає **$20**. Ставка-собівартість: на
>   рівні проєкту/людини/відділу — структуру продумати (власник відкритий: або
>   привʼязка до проєкту, або чисто на стороні працівників).

Доповнення власника (11.06): **задачі, ВКЛЮЧЕНІ в абонплату.** Клієнт платить
фіксовану абонплату ($100/міс) → у рамках неї команда виконує роботи; ці задачі
створюються НА ПРОЄКТІ, падають у канбан виконавцям як звичайні, по них логується
час, але вони **НЕ білляться окремо** (режим `included_in_subscription`,
zero-billed). Їхні години = собівартість проєкту → маржа абон-проєкту =
абонплата − Σ(год × ставка-собівартість). Власник бачить, чи абонплата вигідна.

## 2. Модель даних (Prisma-ескіз)

### 2.1. Нові сутності

```prisma
enum ProjectBillingModel {
  fixed_monthly_advance // абонплата; нарахування ЗАВЖДИ авансом на початку циклу
  hourly_prepaid        // погодинка з авансом (гейт 02-В)
  hourly_postpaid       // погодинка по факту: нарахування при закритті циклу
}

enum ProjectBillingCycle {
  monthly_day_n // кожного N-числа місяця (cycleDay)
  weekly_day_x  // щотижня у день X (cycleWeekday; кейс власника — «щопонеділка»)
  manual        // «здав проєкт — закрив руками — сформував документи»
}

/// Фінансовий проєкт клієнта (05-ПРОЕКТИ). Контейнер фін-моделі між Company
/// та Orders/Charges: договір, валюта, цикл, ставки, маржа — все per-проєкт.
model Project {
  id        String  @id @default(uuid())
  agencyId  String
  companyId String
  company   Company @relation(fields: [companyId], references: [id])
  name      String                    // «Оренда», «Програмування», …
  type      String?                   // П8 ✅: вільний текст-категорія (довідник — на SaaS-фазі)

  billingModel     ProjectBillingModel
  currency         String  @default("USD")          // per-проєкт (В3), НЕ Company.currency
  abonAmount       Decimal? @db.Decimal(12, 2)      // fixed_monthly_advance: сума абонплати за цикл
  clientHourlyRate Decimal? @db.Decimal(10, 2)      // hourly_*: клієнтська ставка ($30 у прикладі)

  billingCycle ProjectBillingCycle @default(monthly_day_n)
  cycleDay     Int?      // 1..28 для monthly_day_n
  cycleWeekday Int?      // 1..7 (ISO; 1=понеділок) для weekly_day_x
  nextCycleAt  DateTime? @db.Timestamptz(3) // якір наступного закриття (патерн CompanyService.nextChargeAt); null для manual

  paymentTermsDays Int?     // 05-Г; null → дефолт компанії → дефолт агенції
  legalEntityId    String?  // 20-Д: юр-особа агенції для договорів/рахунків; null → дефолтна юр-особа
  // legalEntity   LegalEntity? — модель LegalEntity йде окремою міні-спекою 20-Д (передумова)

  contractRequired   Boolean @default(false)  // дефолт залежить від billingModel — див. §5
  contractDocumentId String? // Document(type=contract) / завантажений підписаний (06-Б upload)

  requiresApproval Boolean?              // 02-А; null → дефолт компанії
  advanceGatePct   Decimal? @db.Decimal(5, 2) // 02-В; має сенс для hourly_prepaid (і fixed — аванс 100%)

  includedHoursCap Decimal? @db.Decimal(8, 2) // ГІБРИД (П1, 17.06): абонплата покриває N год; понад → clientHourlyRate. Конфіг закладено; генерація overage — P-2 cycle-engine

  active    Boolean  @default(true)
  createdAt DateTime @default(now()) @db.Timestamptz(3)
  updatedAt DateTime @updatedAt @db.Timestamptz(3)

  executorRates ProjectExecutorRate[]
  orders        Order[]
  charges       ServiceCharge[]

  @@unique([companyId, name])
  @@index([agencyId])
  @@index([agencyId, active])
  @@index([companyId])
  @@map("projects")
}

/// Override ставки-СОБІВАРТОСТІ виконавця на проєкті (12-А). Якщо рядка немає —
/// fallback на персональну ставку працівника (ExecutorRate.hourlyRate, 12-КОМПЕНСАЦІЇ).
model ProjectExecutorRate {
  id             String   @id @default(uuid())
  agencyId       String
  projectId      String
  project        Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
  executorId     String
  executor       Profile  @relation(fields: [executorId], references: [id], onDelete: Cascade)
  costHourlyRate Decimal? @db.Decimal(10, 2) // собівартість год на ЦЬОМУ проєкті ($10 у прикладі)
  currency       String   @default("USD")
  zeroCost       Boolean  @default(false)    // 22: «без собівартості / весь дохід агенції» — перекриває все, cost=0
  createdAt      DateTime @default(now()) @db.Timestamptz(3)
  updatedAt      DateTime @updatedAt @db.Timestamptz(3)

  @@unique([projectId, executorId])
  @@index([agencyId])
  @@map("project_executor_rates")
}
```

### 2.3. Резолюція ставок (канон)

Для кожного `TimeLog` на замовленні з `projectId`:

- **Клієнтська ставка** (дохід): `Project.clientHourlyRate`. Для zero-billed
  задач абонплати — `0` (дохід циклу = `abonAmount`). Для legacy-замовлень без
  проєкту — `Order.hourlyRate` (як зараз).
- **Собівартість** (каскад, перший збіг перемагає):
  1. `ProjectExecutorRate.zeroCost = true` → **0** (весь дохід — агенції);
  2. `ProjectExecutorRate.costHourlyRate` (override на проєкті);
  3. `ExecutorRate.zeroCostDefault = true` → **0** (owner/партнери, 22);
  4. `ExecutorRate.hourlyRate` (базова ставка працівника, 12-КОМПЕНСАЦІЇ);
  5. немає нічого → **0** + ворнінг у UI («ставку не задано») — маржа завищена свідомо, не блокуємо логування.

### 2.4. Заміна CompanyService на Project (П6 ✅ — БЕЗ міграції)

Канон recurring сьогодні (код S5-03b) — `Service → CompanyService → ServiceCharge`;
генерація — `recurringCharges.ts` по якорю `nextChargeAt`, ідемпотентність через

## 3. Білінг-цикли (звʼязка з 06-В)

Двигун — еволюція наявного `generateRecurringCharges` (той самий патерн:
якір `nextCycleAt`, `MAX_CATCHUP_PERIODS`-backstop, ідемпотентність через
`@@unique([projectId, periodStart])`, кросс-тенантний cron + ручний replay).

**Закриття циклу** (cron щодня, `WHERE nextCycleAt <= now() AND active`):

| Крок                    | fixed_monthly_advance                                                                                   | hourly_postpaid                                                                           | hourly_prepaid                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 1. Нарахування          | `ServiceCharge{projectId, amount: abonAmount}` **авансом на НАСТУПНИЙ період** (абонплата завжди аванс) | `ServiceCharge{amount: Σ(год циклу × clientHourlyRate)}` **за минулий період** (по факту) | аванс виставляється при старті робіт (гейт 02-В); закриття циклу — звірка факту проти авансу, донарахування різниці |
| 2. dueDate              | `paymentTermsDays` від дати виставлення (05-Г) → dunning 05-Б                                           | так само                                                                                  | так само                                                                                                            |
| 3. Автодокументи (06-В) | рахунок на період + **акт за минулий цикл** (виконані роботи, год по zero-billed задачах)               | рахунок + акт з деталізацією годин                                                        | акт звірки авансу                                                                                                   |
| 4. Доставка             | email компанії «для документів» (06-Б) + Telegram (06-Г); трекінг доставки                              | так само                                                                                  | так само                                                                                                            |
| 5. Зсув якоря           | `nextCycleAt += 1 міс` (на cycleDay)                                                                    | `+1 міс` або `+7 днів` (weekly)                                                           | так само                                                                                                            |

Режими запуску закриття:

- **`monthly_day_n`** — авто кожного N-числа (cycleDay 1..28).
- **`weekly_day_x`** — авто щотижня у день X; кейс власника: «щопонеділка
  авто-закриття зданих задач + відправка документів».
- **`manual`** — `nextCycleAt = null`; кнопка «Закрити цикл» у Workspace
  («здав проєкт — закрив руками — сформував документи») викликає той самий
  код закриття з `periodStart/End`, що їх задає owner.

Автосписання з передоплати (05-Д): нове нарахування циклу гаситься з
`moneyBalance` через наявний `PaymentAllocation`/`refreshMoneyBalance` — без змін
механіки, лише `chargeId` тепер може вказувати на проєктний charge.

Журналювання: кожен запуск двигуна — рядок у `CronRun` (21-А) — грошовий
автоцикл, фейл має алертити.

## 4. Маржа

### 4.1. Формули (двигун — 22-Д cost allocation, піднятий у ядро)

Для проєкту `P` за період `[t1, t2]` (цикл або довільний діапазон звіту):

```
виручка(P)      = Σ ServiceCharge.totalAmount (projectId = P, period ∈ [t1,t2])     // accrual
собівартість(P) = Σ по TimeLog замовлень проєкту: hours × costRateSnapshot          // §2.3
маржа(P)        = виручка(P) − собівартість(P)
маржа%          = маржа(P) / виручка(P)
```

- Для абон-проєктів собівартість включає години **zero-billed** задач — саме так
  власник бачить, «чи абонплата вигідна» (приклад: $100 абонплата − 6 год × $12 = $28 маржі).
- Для погодинних — перевірка прикладу власника: 1 год → виручка $30, собівартість
  $10, маржа $20. Per-виконавець розріз: групування тих самих TimeLog по `executorId`.
- **Валюти:** проєкти в різних валютах; зведені звіти — конвертація в USD по
  `exchange_rates` (патерн `Payment.amountUsd`: снапшот курсу, не latest).
  **П7 ✅:** курс для собівартості фіксується на **дату TimeLog** (`costRateUsd`-снапшот),
  узгоджено зі снапшотом ставок П5.
- **П2 ✅:** маржа рахується **accrual** (по нарахуваннях) **+ окремий індикатор
  «оплачено N%»** поруч (видно і нараховане, і реально отримане).

### 4.2. Реферал-працівника (12-РЕФЕРАЛ-ПРАЦІВНИКА)

Працівник привів клієнта (`Company.referredByEmployeeId`) → отримує
налаштовуваний **% від ЧИСТОГО доходу** агенції з цього клієнта. Приклад
власника: клієнт платить $20/год, виконавець коштує $10/год → чистих $10/год →
% рефереру. **Неважливо, хто виконує роботи — важливо, хто привів.**

```
чистий_дохід(клієнт, період) = Σ маржа(P) по всіх проєктах клієнта   // та сама формула §4.1
реферал_бонус = чистий_дохід × refPct (per-agency налаштування)
```

Нараховується у `ExecutorPayout.referralBonusAmount` окремим рядком виплати.
**П4 ✅:** рівень агрегації — **по клієнту цілком, один %** (`чистий_дохід(клієнт)`
вище). Per-проєкт/замовлення — не робимо.

### 4.3. Видимість собівартості (22-нюанси)

- Собівартість/маржа видимі **адміну агенції** (на SaaS — тенант-адмінам):
  загалом і в розрізі проєкту.
- Виконавці НЕ бачать клієнтських ставок і маржі — лише свої ставки/виплати.
- Прапорець «нульова собівартість»: у owner-а за замовчуванням
  (`ExecutorRate.zeroCostDefault`), owner може призначити будь-кому
  (партнери-співвласники); per-проєктне перекриття — `ProjectExecutorRate.zeroCost`.

## 8. Погодження вартості — 3 режими + counter-offer (рішення власника 2026-06-19)

> Розширює В11 (02-А/02-В). Виявлено в обговоренні: погодження «оцінки перед стартом»
> (02-А, вже збудовано) НЕ покриває другий реальний сценарій — погодження **фактичної
> суми перед виставленням рахунку**. Власник сформулював потребу як **вибір із 3 режимів**.

### 8.1. `approvalMode` — один перемикач, каскад `Agency → Company → Project → Order`

| Режим        | Зміст                                                           | Гейт                                                                               | Стан            |
| ------------ | --------------------------------------------------------------- | ---------------------------------------------------------------------------------- | --------------- |
| `none`       | робота + рахунок без погоджень (поточна поведінка)              | —                                                                                  | дефолт          |
| `upfront`    | клієнт погоджує **оцінку до старту** роботи                     | блок `→ in_progress`, поки не approved                                             | ✅ 02-А (є)     |
| `on_actuals` | працюємо по факту → погоджуємо **фінальну суму перед рахунком** | нарахування народжується `draft`, **не входить у moneyBalance**, доки не погоджено | 🔜 новий Гейт-2 |

Резолюція: `effective = firstNonNull(order, project, company, agency, 'none')`, снапшот на
момент створення замовлення / випуску нарахування (immutable далі — як `requiresApproval` нині).
Під капотом — дві ортогональні машини (pre-work + pre-invoice), власнику показуємо **один вибір**.

### 8.2. Approver рахунку — налаштовується (`invoiceApprover`)

- `client` — клієнт-owner / делегат з `can_approve_estimates` погоджує у порталі (як 02-А);
- `internal` — власник/фінансист сам переглядає й випускає `draft`-нарахування (self-review перед відправкою).

Та сама стан-машина (`OrderApprovalStatus` pending→approved|rejected), різний гейт прав.

### 8.3. Counter-offer — наскрізний для `upfront` і `on_actuals`

Рішення погодження несе **`approvedAmount`**. Якщо погоджено меншу суму `Y` за оцінку `X`:
`Y` стає виставленою сумою, різниця `X − Y` фіксується як поступка (переюз P-10
`manualDiscountAmount`) з аудитом (хто/коли/коментар). Так на замовленні видно **три числа**:
**очікувано** (оцінка `X`) → **фінально виставлено** (`Y`) → **реально сплачено** (аллокації).
Ефективність (виставлено − собівартість) уже рахує маржа-движок P-9.

### 8.4. Реалізаційний ескіз (мінімальний, без нових таблиць)

- `ServiceCharge` +`approvalStatus`/`approvalDecidedAt`/`approvalDecidedById`/`approvalComment`
  (дзеркало 02-А полів Order) + `approvedAmount?`; `moneyBalance = Σ платежі − Σ charges WHERE
approvalStatus IS NULL OR approved` (draft/rejected — фінансово інертні; backfill NULL → zero-risk).
- `approvalMode` enum (`none|upfront|on_actuals`) на Agency/Company/Project (+Order override),
  `invoiceApprover` enum (`client|internal`); deprecate `Project.requiresApproval` → expand/contract.
- Гейт-2: у `buildChargeRow`/`closeProjectCycle`/prepaid/overage — стампити `approvalStatus`;
  блок генерації документа для `draft` (як контракт-гейт 409); роути `POST .../charges/:id/approval`
  (portal + workspace). Counter-offer вливається в `applyChargeDiscount`.
