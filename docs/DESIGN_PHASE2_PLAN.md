## Трек A — Conformance: довести реалізоване до дизайну (48 RISK)

Реалізовані екрани, що «виглядають/поводяться не так». Пріоритет за видимістю для тестувальника.

- **A0 · Бренд листів (глобальний баг).** `packages/notifications/src/email/render.ts` хардкодить IBM-Carbon
  синій `#0F62FE` (+ `#1F2933`/`#6B7785`/`#F4F6FA`) замість лаймових `--wf-*`. Усі 15 листів виглядають
  не-брендово. **Найдешевший і найпомітніший фікс** — винести палітру у бренд-токени (email-safe inline).
- **A1 · Orders/Portal approval-банер** (`OrderDetailPage.tsx`) — зараз пасивний текст; додати кнопки
  «Погодити»/«Запросити правки» + розбивку оцінки (бекенд `decideOrderApproval.ts` уже є).
- **A2 · Clients** — `ClientsPage` показує `Клієнт · <id8>` без імен/тіру/боргу/статусу; `ClientDetailPage`
  без табів. Підтягнути реальні поля (потребує clients-CRUD — див. Трек B/28).
- **A3 · Дрібні стани** — багато екранів без empty/loading/error/scan-станів із мокапа (файли,
  чат-context-menu, referral-копірайт, finance-порожні стани, wallet-hero). Пройтись по списку RISK у матриці.
- **A4 · Order docs-tab** — захардкоджені дані замість API; чат-бабл без markdown-light/⋯-меню.

Деталі кожного RISK-рядка — у `DESIGN_COVERAGE.md` (колонка «Відп.» = ⚠️ RISK + нотатки).

## Трек B — Добудувати екрани, де бекенд уже є (28)

Найдешевше: дані вже віддаються API, лишається UI. Пріоритет за цінністю для власника.

| Пріор  | Модуль           | Що добудувати                                                 | К-сть |
| ------ | ---------------- | ------------------------------------------------------------- | ----- |
| **П1** | 02 Orders        | Канбан (List/Timeline/Board), Triage вхідних, bulk-екрани     | 11    |
| **П1** | 05 Billing       | Модалка «Підтвердити оплату», разова знижка, payment terms UI | 4     |
| **П1** | 20 AdminSettings | Юр-особи агенції (LegalEntity CRUD) + селектор на проєкті     | 2     |
| **П1** | 22 Finance       | Експорт CSV/XLSX, розріз маржі на проєкті, тумблер zeroCost   | 3     |
| **П1** | 28 Clients       | Таб «Проєкти» (embedded fin-projects) у картці 360°           | 1     |
| П2     | 12 Team          | Ростер команди, картка виконавця, панель часу                 | 3     |
| П2     | 06 Documents     | Юр-онбординг компанії (форма реквізитів)                      | 1     |
| П2     | 09/10/13         | Referral-мобільний, manual override тіру, профіль члена       | 3     |

_Усього backend-ready: 28. Точний перелік — секція «Що будувати далі» у `DESIGN_COVERAGE.md`._

Окремо (дизайн ✅, бекенд **partial**, рішення власника): **project360** `/projects/:id`,
**client360 7 табів** `/clients/:id` — найцінніші за ТЗ (28-Б = П1 №1), але потребують доробки API
(clients-CRUD, project-aggregate). Виносимо рішенням: добудувати API → екран.

**Проєкти — клієнтський/внутрішній тип (S6+, backend-blocked).** Дизайн «Проєкти» = клієнтський
(білінг) АБО внутрішній (без білінгу). Наш `Project` завжди client-bound + billed (`companyId` +
`billingModel` обов'язкові), тож «Фін-проєкти» = тільки клієнтський зріз. «Внутрішній» вимагає
nullable-company + опц. білінг + поле «вид» + no-invoice шлях + 7-крок майстер. Рішення власника
(2026-06-24): S5 лишається «Фін-проєкти» (client-only), уніфікація «Проєкти» + перейменування —
коли підемо в бекенд. Деталі — conformance-нот у `DESIGN_COVERAGE.md` (модуль 05, рядок «Майстер
створення Проєкту»).
