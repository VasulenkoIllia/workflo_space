# AUDIT 2026-09 — рольовий прохід фронтенду (дублі · глухі кути · 403)

> Разова звірка «меню ↔ маршрути ↔ перевірки прав бекенду» для кожної ролі (27.09.2026, read-only
> агент + ручна верифікація ключових тверджень). Привід — скарга власника: «дублювання вкладок,
> не повна нормальна логіка роботи». Remediation-loop: audit → fix (черга ROLE-\* у ROADMAP) →
> re-audit. Скорочення: `ws/` = `apps/workspace/src/`, `pt/` = `apps/portal/src/`, `api/` =
> `apps/api/src/`.

## A. Рольова модель (як у коді)

| Роль                     | Джерело                                         | Суть                                                                                                                                     |
| ------------------------ | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Власник агенції          | `AgencyMember.role=owner`; `requireOwnerAgency` | усе                                                                                                                                      |
| Менеджер                 | `AgencyMember.role=manager`                     | `MANAGER_BLOCKED` (`api/auth/can.ts`) + ручні «внутрішній, але не менеджер»; без фінансів/налаштувань/інвайтів/vault; **приймає роботу** |
| Виконавець               | `AgencyMember.role=executor`                    | внутрішній; дошка — лише своя команда                                                                                                    |
| Тімлід                   | executor із `Team.leadId` (окремої ролі нема)   | лише колонки СВОЄЇ дошки; роботу не приймає, KPI не бачить. Бекенд-меседжі кажуть «тімлід», маючи на увазі менеджера (D10)               |
| Власник компанії-клієнта | `CompanyMember.role=owner`                      | усе в порталі                                                                                                                            |
| Учасник компанії         | `CompanyMember.role=member` + JSON-прапорці     | прапорці ніде не пишуться і не віддаються в `/auth/me` → учасник завжди `{}`: без білінгу й погодження                                   |

## B. Головні знахідки (пріоритет)

### High

- **D1 «Команда» для виконавця/тімліда → тихий редирект.** Меню `omx`, маршрут пускає лише
  owner+manager (`ws/App.tsx`); read-only ростер тімліда (TEAM-ADMIN-2) недосяжний.
- **D2 Менеджер: 403 на `GET /workspace/companies`** → «Нове замовлення» завжди disabled,
  конвертація ліда неможлива, клієнти «Клієнт · xxxx», тост у календарі.
- **D3 Задачу неможливо створити з UI** (хуки create/update/delete не використовуються; таб
  «Задачі» прибрали, empty-state дошки досі на нього посилається).
- **D4 Агенція не може завести клієнта** — компанію створює лише самореєстрація; лід →
  конвертація потребує наявної компанії → глухий кут.
- **D5 Учасник порталу** — меню не фільтрується, кнопки «Погодити» (кошторис/рахунок) дають 403,
  «Оплатити» — вічний skeleton; власник компанії не може видалити учасника / змінити права.

### Medium

- **D6** `/settings` лише для власника → менеджер/виконавець не мають де налаштувати сповіщення,
  Telegram, сесії.
- **D7** Менеджер на «Команді»: «Запрошення», KPI-смуга, «Заробіток» у профілі — 403.
- **D8** Посилання на недоступні маршрути (`/projects/:id` із замовлення/⌘K/дашборду) → редирект.
- **D9** Виконавцю пропонуються переходи статусу, які бекенд відхиляє (готово/drag у «готово»).
- **D10** Термін «тімлід» подвійний (менеджер у бек-меседжах vs `Team.leadId`) — рішення власника.
- **D11** Помилка показується як порожній стан (портал projects/company/…; ws reports/board/…).
- **D12** Менеджер бачить фінанси (нетто-виручка на картці виконавця; генерація рахунків) — політика?

### Low

D13 `/orders?status=review` не фільтрує · D14 подвійні тости (~30 локальних onError поверх
глобального) · D15 імʼя клієнта з першого замовлення · D16 менеджер «Погодити» власну відпустку →
403 · D17 перемикач UA/EN нічого не робить · D18 портальний `/settings` поза `CompanyGate`.

## C. Дублі (що лишити)

1. Керування підрозділами: дошка «⚙ команди» **і** Команда→«Підрозділи» → лишити `/team`.
2. Два таби «Підрозділи» (Звіти — аналітика, Команда — оргструктура) → у звітах «Продуктивність підрозділів».
3. Три місця зміни статусу замовлення → здача/приймання лише в `AcceptanceCard`, `StatusControl` фільтрувати за роллю.
4. Три «мої задачі» з різними сутностями → дашборд виконавця = «Мої замовлення».
5. Дебітори в трьох місцях із двох ендпоінтів → джерело — Білінг, решта лінкує.
6. Виручка з трьох ендпоінтів (MoM/revenue/P&L) → одне визначення, звірити цифри.
7. Два «каталоги» (`/services` у «Фінансах» + Налаштування→«Каталоги») → перенести в Налаштування.
8. 2FA двічі (Профіль + Налаштування→«Акаунт»).
9. Група меню «Фінанси» на 10 пунктів (вкл. «Контент», «Оголошення») → розбити.
10. Портал: дані компанії на трьох сторінках → `/company` як дім (профіль+реквізити+учасники).
11. Портал: «баланс» і платежі в Білінгу **і** Гаманці; заголовок «Фінанси» ≠ пункт «Рахунки й борг».
12. Тема/мова в топбарі **і** в налаштуваннях порталу (топбар не зберігає на сервері).
    13–14. Меню користувача дублює сайдбар; однакові іконки різних пунктів (low).

## D. Бекенд дозволяє більше, ніж UI (окремий security-review)

Виконавець може запрошувати виконавців, видаляти замовлення, редагувати проєкти/кошториси/
юр-особи; менеджер — каталог послуг. Перевірити навмисність.

## F. Зрізи ремедіації

1. **ROLE-NAV** (S, фронт): D1, D6, D8, D9, D13, D16.
2. **MANAGER-OPS** (S, бек+фронт): D2, D7 (+ рішення D10/D12).
3. **PORTAL-MEMBER** (M): прапорці в `/auth/me`, фільтр меню, стан «доступно власнику», гейт кнопок
   погодження/оплати, реквізити лише власнику, керування учасниками (DSN-6 перетин).
4. **CORE-FLOWS** (M): створення задач (D3); «+ Клієнт» + лід → нова компанія (D4).
5. **DEDUP-IA** (S/M): C1–C11 + приховати EN до i18n (D17).
6. **STATES-HYGIENE** (S): `isError` (D11), подвійні тости (D14), імʼя клієнта (D15), CompanyGate (D18).
