# ТЗ дизайнеру 2026-06 — зведення нових/змінених екранів (прохід власника)

> **Призначення:** єдине ТЗ для дизайнера на всі нові та змінені екрани, що випливають
> з проходу власника по 29 модулях. **Канон-джерело:** `docs/MODULE_REVIEW_2026-06.md`
> (рядки «Для ТЗ дизайнеру» + рішення з впливом [екран]/[бек+екран]). Тут нічого не
> додано поза REVIEW — лише структуровано і пріоритезовано.
>
> **Правило процесу:** у проєкті функціонал, логіка і дизайн тримаються на одному рівні.
> Тому **кожен новий екран спочатку лягає в дизайн-систему, потім у код**:
> мокап → `design/project/` → токени `--wf-*` / класи `.wfp-*` → реалізація.
> Головний док дизайну — `docs/DESIGN_SYSTEM.md` (референс; цим ТЗ не змінюється).
> Попередній MVP-handoff — [`DESIGN_TODO.md`](DESIGN_TODO.md) (база, закрита 02.06); цей файл — **розширення** з проходу власника.
>
> **Легенда пріоритетів:**
>
> - **П1** — блокує найближчі спринти: фін-модель 2.0 (05-ПРОЕКТИ), документи (S6), білінг-екрани.
>   Критична залежність плану: проєкти (05) + юр-особи (20-Д) + реквізити клієнта (06-Б) +
>   payment terms (05-Г) мають лягти ДО/РАЗОМ зі спринтом документів S6.
> - **П2** — наступна хвиля (чат/медіа, нотифікації, пошук, звіти, vault, inbox тощо).
> - **П3** — SaaS-фаза / свідомо пізнє (тури, лендінг-пресети, passkeys-UI, пізні фази модулів).

## 1. Пріоритет П1 №1 — Картка клієнта 360° (28-Б)

**Найбільше дизайн-завдання проходу.** Наголос власника: «особливо важлива для розуміння
всіх даних про клієнта і створення проєктів» — центральний екран Workspace, з якого
видно і керується все по клієнту. Сім табів:

| Таб            | Зміст                                                                                                                                                                                                                                               | Звʼязки з рішеннями                                                                                       |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Огляд**      | Зведення по клієнту: ключові показники, прапорці ризику (борг/неактивність/овердʼю) — бейджі, теги клієнта + сегменти                                                                                                                               | 28-Г (ризик-бейджі + attention-дашборд), 28-Д (теги/сегменти), 12-РЕФЕРАЛ (поле «хто привів клієнта»)     |
| **Люди**       | Члени компанії клієнта + панель адмін-дій: скидання пароля, деактивація, зміна email, видалення члена                                                                                                                                               | 28-А (адмін-дії; запит прийшов з модуля 09)                                                               |
| **Проєкти**    | Список фінансових проєктів клієнта + створення проєкту: білінг-модель (fixed_monthly_advance / hourly_prepaid / hourly_postpaid), валюта, ставки, договір (обовʼязковий/опційний), білінг-цикл (N-число / щотижня / вручну), вибір юр-особи агенції | 05-ПРОЕКТИ (ядро фін-моделі 2.0), 06-В (білінг-цикли), 20-Д (юр-особи), 12-А (override ставок на проєкті) |
| **Фінанси**    | Борг, LTV, маржа; payment terms клієнта; дії сторно/повернення/списання боргу; розрізи по проєктах                                                                                                                                                  | 05-Г (payment terms), 05-В (refund/credit-note/write-off), 22-Д (собівартість/маржа), 05-Б (overdue)      |

| **Секрети**    | Ключі/доступи клієнта (типізовані картки), журнал доступів                                                                                                                                                                                          | 17-А (двосторонній ввід), 17-Д (типи), 17-Б (журнал)                                                      |
| **Активність** | Внутрішні нотатки + таймлайн подій по клієнту                                                                                                                                                                                                       | 28-В                                                                                                      |

## 7. SaaS-фаза (на потім) — П3

Свідомо відкладено рішеннями власника; у дизайн-беклог, не в поточну чергу:

1. **Лендінг-пресети + міні-CMS тенанта (11-ЛЕНДІНГ-ПРЕСЕТИ).** Кілька пресетів
   лендінгу для тенанта + **узгоджена звʼязка 3-х дизайнів** (лендінг + портал +
   воркспейс однією темою). Зараз основна тема — «IT/код/термінал»; додати 2-3
   нейтральні шаблони + кольорові схеми; у блоки можна додавати картинки. + SEO-набір
   тенанта (слаги, мета), GTM / Facebook Pixel per-tenant. (→ SAAS.md, E-серія E8.)
2. **Продуктові тури (29-ТУРИ).** Багаторівневі guided-тури «за руку»: клієнт у Portal,
   виконавець у Workspace, onboarding нового owner-тенанта на SaaS. Рівні екскурсії
   залежать від ролі і відкритого функціоналу. Реалізація — після закриття функціоналу;
   дизайн-ТЗ на тур-оверлеї окремо.
3. **Passkeys-UI (01-Е).** Таблиця `WebAuthnCredential` закладається в схему зараз,
   UI входу без пароля — окремим пізнішим ТЗ.
4. Суміжне П3 з таблиць вище: налаштування пошти тенанта (08-Г), «написати ліду
   з картки» (26-Г).

## 8. Відкриті питання дизайнеру

> Власник-залежні питання (1-4 у попередній версії) закрито 2026-06-12 —
> `OPEN_QUESTIONS_2026-06.md`. Нижче лишилось ЧИСТЕ дизайн-виконання.

**✅ Закрито власником (рішення для дизайну):**

- **Розміщення «Проєктів клієнта» (С1):** І таб у картці клієнта 360°, **і окремий
  розділ-список** у Workspace (як для замовлень). Флоу «створення проєкту» — з обох місць,
  наголос власника на створенні з картки клієнта.
- **Ліміт годин в абонплаті (П1):** поле є, але **логіка понадліміту — фаза 2** → у UI
  зараз показувати спожиті/включені години інформативно (прогрес), БЕЗ блоку/доплати.
- **Рівень ставки-собівартості (С2):** форма ставок під **триярус** — базова ставка
  людини (профіль виконавця) → override на проєкті → прапорець «без собівартості»
  (zeroCost). Відділ — лише дефолт ставки.
- **Magic-link (С3):** лише Portal /login; у Workspace варіант «Увійти за посиланням»
  НЕ показуємо.

**Лишається дизайн-виконання (рішення власника не потрібне):**

1. **Погодження hourly-оцінки (02-А).** Для нефіксованої ціни погоджується ставка +
   оцінка годин (орієнтир): як візуально відрізнити від fixed-погодження і донести
   клієнту, що години — орієнтир, а не зобовʼязання.
2. **Формати документів UA vs EU (06-Е).** «Не лише переклад — різні формати»:
   потрібні референси/вимоги до європейського комплекту перед стартом другого
   PDF-комплекту.
3. **Матриця «категорія листа → відправник» (08-Г).** Як компактно подати матрицю
   категорій листів × відправників у налаштуваннях пошти тенанта (3 рівні підключення
   - статус DNS-верифікації поруч).
