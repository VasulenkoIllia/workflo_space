## Легенда

- **Пріоритети:** **П1** — блокує найближчі спринти (фінмодель 2.0 / документи / білінг-екрани);
  **П2** — наступна хвиля (чат-медіа, нотифікації, пошук, звіти, vault, inbox); **П3** — SaaS-фаза / пізнє
  (тури, лендінг-пресети, passkeys-UI).
- **Статус мокапа:** `РЕЮЗ` — наявний беремо 1:1; `РОЗШИР` — є, домалювати блоки/стани; `НОВЕ` — екрана нема.
- **Ролі:** Workspace — owner / manager (без фінансів і налаштувань) / executor (свої задачі); + view-as
  (owner→клієнт, super-admin→тенант). Portal — client-owner / client-member (за `can_view_all_tasks` + 02-Е′).
- **Модульність (ADR-008):** кожен пункт навігації несе `moduleKey` + `minRole`; недоступний модуль/роль —
  пункт **прихований** (не disabled). Лендінг і Client Portal — per-план флаги; Workspace — завжди on.

# Частина I — Інформаційна архітектура (навігація і розміщення)

## ІНФОРМАЦІЙНА АРХІТЕКТУРА — навігація і розміщення модулів/блоків (усі 3 апки)

> **Призначення розділу.** Зафіксувати логічне розміщення кожного модуля/блоку в навігації трьох поверхонь (Landing / Portal / Workspace) — щоб дизайнер малював екрани в межах єдиного, role-aware каркаса, а не складав сайдбар «на око». Поточний `WORKSPACE_NAV` у `product-shell.jsx` — плоский dump 30+ пунктів (мішанина owner / admin / особистих / dev-debug екранів). Ця IA його **переструктуровує** (групи, порядок, видимість за роллю), не змінюючи дизайн-систему.
>
> **Канон:** ADR-008 (модулі/тарифи/ролі owner/manager/executor, view-as, граф залежностей), `MODULE_REVIEW_2026-06.md` (20-А manager, 20-Б view-as), `PROJECTS_SPEC.md` (фін-проєкти, маржа-розрізи), `LEGAL_ENTITY_SPEC.md` (20-Д), `DESIGN_SYSTEM.md` (Engineer-s Cut, режим A).
>
> **Реюз каркаса:** `eco-nav.jsx` (верхній ecosystem-бар, спільний для всіх поверхонь) — **РЕЮЗ**; `product-shell.jsx` `AppShell/Sidebar/Topbar` — **РЕЮЗ компонентів**, але `WORKSPACE_NAV`/`PORTAL_NAV` як конфіг — **ПЕРЕРОБКА** (нова групова структура + поле ролі/модуля на кожному пункті).

### 0. Базові принципи IA (для всіх 3 апок)

1. **Три рівні навігації.** (1) `eco-nav` — перемикання між поверхнями екосистеми (landing / portal / workspace / documents / brandbook) — **РЕЮЗ** `eco-nav.jsx`; на проді клієнт бачить лише дозволені йому вкладки. (2) Сайдбар поверхні — розділи всередині апки. (3) Таби/under-nav усередині розділу (напр. 7 табів у Картці клієнта 360°).
2. **Естетика shell.** Engineer-s Cut, режим A (`aesthetic='A'`): віконний chrome (traffic-dots, тайтл `work.workflo.space — bash · 1440×900`), статус-бар знизу (`main · поверхня · шлях · час · тема`), групи сайдбару як коментарі `// розділ` (lowercase). Токени — `--wf-*`; класи продукту — `.wfp-*`. Лайм-акцент за замовчуванням (свапабельний пресет).
3. **Гейтинг = entitlements × роль (ADR-008).** Кожен пункт навігації несе `moduleKey` + `minRole`. Пункт **прихований** (не disabled), якщо: модуль не входить у тариф тенанта (`featureEnabled=false`) АБО роль не має доступу. Дизайнер малює один сайдбар із усіма групами + варіанти «згорнутих» станів для manager/executor (нижче).
4. **Топбар (РЕЮЗ `Topbar`).** Хлібні крихти зліва (`/` як `wfp-crumb-sep`), праворуч: дії контексту → `⌘K`-пошук → дзвоник-нотифікації → аватар. View-as вмикає **жовтий банер** над топбаром (див. 2.6).

```

│  Sidebar    ├──────────────────────────────────────────────────────────────────────────────────────────────────────┤
│  (wfp-sb)   │  [view-as банер — лише коли активний]                                                                  │
│  розділи +  │  Content (wfp-content)                                                                                 │
│  групи      │     — list / detail / 360-hub / settings                                                              │
│             │                                                                                                       │
│  ───────    │                                                                                                       │
│  foot:      │                                                                                                       │
│  Portal →   │                                                                                                       │
│   company-  │                                                                                                       │
│   switcher  │                                                                                                       │
│  Work →     │                                                                                                       │
│   user+role │                                                                                                       │
├─────────────┴──────────────────────────────────────────────────────────────────────────────────────────────────────┤
│  statusbar: ● main · work.workflo.space · /clients/acme/projects · 14:32 · dark                                       │

```

- **Топбар** (`Topbar`, РЕЮЗ): крихти = шлях у IA; праві дії контекстні (напр. «+ Проєкт» на картці клієнта). **АДАПТИВ:** на mobile крихти стискаються до поточного рівня + «‹ назад»; іконки-дії ховаються у «…».
- **Сайдбар** (`wfp-sb`, РЕЮЗ): головка — wordmark + sub (`work`/`portal`); тіло — групи (`wfp-sb-group` = `// розділ`); підвал — **Portal:** перемикач компанії (мульти-компанія, `wfp-sb-company`); **Workspace:** користувач + роль + версія (`wfp-sb-user`, напр. `owner · v0.6.2`). Роль у підвалі — **точка входу у view-as** (owner).
- **Контент** (`wfp-content`): єдиний скрол; патерни — list, detail, **360-hub** (таби), settings.
- **СТАНИ shell:** loading — skeleton сайдбару (`skeletons.jsx`, РЕЮЗ) + shimmer контенту; empty/error/permissions — на рівні розділу (нижче). Сайдбар при `403` не зникає — прихований лише недоступний пункт.

### 2. Workspace IA — role-based структура сайдбару

> **Реорганізація з мотивацією.** Власник вимагав «логічне розміщення». Поточний flat-список зливає операційні, фінансові, контентні, адмін- і dev-debug пункти. Нова структура — **7 логічних груп**, упорядкованих за частотою операційного використання (зверху — щоденне, знизу — налаштування/адмін). Dev-debug екрани (`403`, `dlq`, `trash`, `forbidden`) виносяться з основної навігації у Адмін-підрозділ / службову зону.

#### 2.2 Картка клієнта 360° — внутрішня під-навігація (таби)

`/clients/:id` — **detail-hub**, шапка (назва, бейджі ризику 28-Г, теги/сегменти 28-Д, «хто привів» 12-РЕФЕРАЛ) + горизонтальні таби (`wfp-tabs`):

```
Огляд · Люди · Проєкти · Фінанси · Документи · Секрети · Активність
  28-Г   28-А    05-С1     05-Г+22-Д  06        17       28-В
```

- Таб **Проєкти** = вбудований список фін-проєктів клієнта + CTA «+ Проєкт» (форма: білінг-модель, валюта, ставки, договір, цикл 06-В, **селектор юр-особи 20-Д** з дефолтом).
- **Видимість табів за роллю:** Фінанси-таб — owner-only; Документи/Секрети — owner+manager; решта — усі з доступом до клієнта. manager бачить картку без вкладки «Фінанси».

### 0. ПРИНЦИП: лендінг = набір themeable-блоків під майбутню CMS

Це **настанова дизайну**, не код. Кожен блок головної та підсторінок проектується як **самодостатній, модульний, themeable-блок**, який:

1. **Мапиться на майбутній `LandingContent.block`** (14-landing §C: `hero | services | cases | pricing | faq | cta | …`). Один namespace блок-типів ділиться між дизайном і моделлю CMS. Тобто дизайнер дає кожному блоку **стабільний `block`-ключ** (див. таблицю нижче) — щоб контент-CMS (S14-04, owner редагує блоки без деплою) і майбутні пресети/теми (11-ЛЕНДІНГ-ПРЕСЕТИ, SaaS-фаза) лягли **без перемалювання**.
2. **Тримає контент у слотах, не в коді.** Кожен текстовий рядок, заголовок, метрика, лого, зображення — окремий слот, який читається з `contentJson` (per-locale). Дизайн **не зашиває** конкретні тексти; мокап показує приклад наповнення, але layout валідний для будь-якого вмісту в межах обмежень (min/max довжина — нижче).
3. **Themeable через токени `wf-*`**, ніколи не хардкодить hex (DESIGN_SYSTEM §2). Колір/акцент/фон беруться лише з `--wf-accent / --wf-accent-bg / --wf-accent-soft / --wf-bg / --wf-fg / --wf-fg-muted / --wf-border`. Зміна теми = підміна токенів через `data-theme` (light/dark) + `data-accent` (6 пресетів). **Жоден блок не повинен ламатися при зміні акценту чи теми.**
4. **Має слот під зображення (`media`-слот)**, навіть якщо в основній «термінальній» темі картинки немає (там — ASCII/гліфи). Це закладка під 11-ЛЕНДІНГ-ПРЕСЕТИ: «у блоки можна додавати картинки». Кожен блок описує: де медіа-слот, його співвідношення сторін, fallback коли картинки немає.

**Класова конвенція.** Поточні мокапи використовують префікс `wf-tm-*` (terminal). Для CMS-зрілості рекомендується паралельно тримати **семантичний `block`-атрибут** на корені кожної секції: `data-block="hero"`, `data-block="cases"` тощо (DESIGN_SYSTEM-клас `wfl-*` — лендінг). Це дозволить CMS адресувати блок, а пресету — підмінити стиль. **Дія дизайнера:** проставити `data-block` на кожній секції (зараз є частково — `data-screen-label`).

**АДАПТИВ.** Desktop — повне вікно з max-width контейнером. Mobile (≤480, перевірено на 375): nav згортається — wordmark + бургер; таби в drawer; CTA лишається видимим; status-bar ховається. Терміна-вікно займає всю ширину, padding зменшується.

**ЗВ-ЯЗОК.** 14-landing (каркас), 06-Е (i18n-перемикач), eco-nav (єдність екосистеми).

**Мовний перемикач — критичний нюанс (14-landing Аудит §A).** Перемикач замінює **провідний locale-сегмент** URL (`/uk/...` ↔ `/en/...`), а **не перший збіг `replace`** (інакше зламає шляхи типу `/uk/uk-guide`). Зберігає поточний шлях і query. Контент кожного блоку перемикається per-locale зі слотів (`uk`/`en` поля `contentJson`).

### 2. БЛОК HERO — `block: hero`

**МЕСЕДЖ.** За 1 екран: хто це, що робить, кому, і один наступний крок. Поточний меседж — «автоматизація + AI-агенти для команд, що виросли з Excel».

**ВМІСТ І ПОЛЯ КОНТЕНТУ (слоти CMS):**

- `headline` (H1) — підтримує **варіанти** (зараз `h1_options[]`, A/B). 2–3 рядки, до ~48 симв/рядок. Слот `string[]` per-locale.
- `sub` (підзаголовок, `// …`-формат) — 1–2 речення.
- `cta_primary` — текст + href (default → `portal/register` АБО `#book` для booking-варіанту).
- `cta_secondary` — текст + anchor (`#services` / `#work`).
- `media`-слот: у термінал-темі — `AsciiPortrait` (гліф-портрет) у hero-portrait-slot. У майбутніх пресетах — растрове фото/ілюстрація (співвідношення 1:1 або 4:5). **Fallback без зображення:** ASCII-логотип-кіт (вже є), блок не порожніє.
- `live`-індикатор (status-dot) — опційний бейдж «доступний для проєктів».

**LAYOUT.**

- _Desktop:_ двоколонковий — ліворуч H1+sub+CTAs, праворуч media-slot (portrait). Або центрований one-column, якщо media порожній.
- _Mobile:_ one-column, media зверху/прихований, CTAs на повну ширину (stack).

**СТАНИ.**

- _empty content:_ якщо `headline` порожній — показати default-копірайт із i18n (`landing.json hero.title`), не порожній екран.
- _no image:_ media-slot згортається до ASCII-fallback; H1 центрується.
- _loading:_ boot progress перед hero (вже є).

**THEMEABLE-СЛОТИ.** Акцент — на CTA-primary (`wf-tm-btn--primary`, фон `--wf-accent-bg`), на live-доті (`--wf-accent`), на cursor. H1 — `--wf-fg`; sub — `--wf-fg-muted`. CRT-glow (опц.) керується класом `wf-tm-glow`.

**CTA-ЛОГІКА.** Primary → реєстрація/booking (конфігурується). Secondary → scroll-anchor. На обидва — analytics-події (§13). Якщо в тенанта вимкнено self-register (SaaS) — primary веде на `#contact`.

**ЗВ-ЯЗОК.** 14-landing §1; CTA→01-auth (register) або 14-В (booking). РЕЮЗ `TerminalHero`.

### 11. БЛОК CTA «ЗАБРОНЮВАТИ ДЗВІНОК» — `block: cta_booking` (14-В, ДОДАТИ)

**МЕСЕДЖ.** Низькобар'єрний наступний крок — забронювати безкоштовний дзвінок без листування.

**ВМІСТ (CTA-блок, слоти):** `title` («Готові обговорити?»), `sub` («// безкоштовний discovery-дзвінок · 30 хв»), `button` («Забронювати дзвінок →»), що веде на **`/book/:userSlug`** (booking-сторінка). Тип дзвінка можна передзаповнити (`?type=discovery`).

**LAYOUT.** CTA-блок — band на повну ширину (як `wf-tm-cta-band`). Сторінка booking: _Desktop:_ двоколонка (календар | слоти); _Mobile:_ календар зверху, слоти під ним, типи дзвінка — горизонтальний скрол/stack.

**CTA-логіка.** Вибір слота → confirm-форма (ім'я+email, опц. нотатка) → confirmed. **Подія analytics `booking_confirmed`** (§13).

**ЗВ-ЯЗОК.** **14-В** (booking-CTA на лендингу), бекенд — **модуль 24 / S13-03** (booking-links, генерація `.ics`, Google Meet). РЕЮЗ `BookingPage`; **ДОДАТИ** компактний CTA-блок-band на головній, що веде на сторінку.

### 12. БЛОК КОНТАКТ-ФОРМА — `block: contact` (→ лід, модуль 26)

**МЕСЕДЖ.** Прямий канал «опишіть задачу» з гарантією відповіді того ж дня.

**ВМІСТ (слоти):** Форма (`fields[]`: name, email, тип задачі (select), message (textarea), бюджет (опц.)), `reasons[]` (чек-причини написати), aside-канали (`channels[]`: telegram/mail/globe з primary), `meta` (години, оплата, NDA). Інтро.

**LAYOUT.** _Desktop:_ двоколонка — форма ліворуч, канали+мета праворуч. _Mobile:_ форма зверху, канали під нею.

**СТАНИ (повний набір — критично):**

- _idle:_ форма готова.
- _submitting:_ кнопка `[ надсилаю… ]` disabled + спінер.
- _success:_ інлайн-підтвердження «✓ отримав, відповім сьогодні» (не редірект), форма очищається.
- _error (валідація):_ per-field помилки (email-формат, обов'язкові).
- _error (сервер/спам-відмова):_ загальний банер «не вдалося, напишіть у Telegram» + прямий лінк.
- _rate-limited / Turnstile fail:_ «підтвердьте, що ви не бот».
- _empty:_ — (форма завжди є).

**СПАМ-ЗАХИСТ І LEAD-КОНТРАКТ (14-landing §A, обов'язково).** Дизайн має передбачити:

- **Cloudflare Turnstile**-віджет (невидимий/керований) — слот під капчу перед submit-кнопкою.

## 2. ПРОЄКТИ КЛІЄНТА (05-ПРОЕКТИ · П1) — список, майстер, екран проєкту

### 2.1. Список проєктів — РЕЮЗ `workspace-services.jsx` (`WorkspaceBillingServices` + `BillingSubtabs`)

ВМІСТ: таблиця — проєкт · клієнт · модель · валюта · сума · цикл · `nextCycleAt` · маржа% `[owner]` · статус. Фільтри: клієнт, модель, статус, юр-особа. РЕЮЗ `BillingSubtabs` як підрозділ білінгу. СТАНИ/АДАПТИВ — як 1.3. `[owner; manager без маржі/створення]`. РЕЮЗ.

### 2.2. Майстер створення проєкту (НОВИЙ · ДЕТАЛЬНО)

**Вхід:** «+ Проєкт» з картки клієнта (1.3) або зі списку (2.1, тоді спершу селектор клієнта). Модальний степпер або повноекранна форма (`wfp-field`/`wfl-select`-патерн з `ClientInfo`). **Поля з'являються/ховаються залежно від `billingModel`** (правила обов'язковості — `PROJECTS_SPEC.md §5`):

**Крок 1 — Основа:**

- `name` (обов'язк.), `type` (вільний текст-категорія, П8).
- **Білінг-модель** (radio-карти, обов'язк.): «Абонплата-аванс» / «Погодинка-аванс» / «Погодинка-факт» — кожна з мікроописом («нарахування завжди авансом» / «аванс при старті + звірка» / «по факту при закритті циклу»).
- `currency` (обов'язк., дефолт з компанії).

**Крок 2 — Гроші (залежить від моделі):**

- Якщо `fixed_monthly_advance`: **`abonAmount`** (обов'язк.) + поле `includedHoursCap` (опційне, з підписом «ліміт включених годин — облік зараз, enforce у фазі 2», П1).
- Якщо `hourly_*`: **`clientHourlyRate`** (обов'язк., приклад-плейсхолдер «$30/год»).
- `advanceGatePct` (02-В) — лише для `hourly_prepaid`; для `fixed` n/a (аванс=100%).

**Крок 3 — Білінг-цикл (06-В):** radio — «Кожного N-числа» (`cycleDay` 1..28) / «Щотижня» (`cycleWeekday` 1..7, кейс «щопонеділка») / «Вручну» (`manual` — без `nextCycleAt`, закриття кнопкою). Прев'ю «наступне закриття: …».

**Крок 4 — Договір і юр-особа:**

- **Юр-особа агенції (20-Д, каскад Юр-3):** селектор `LegalEntity` з дефолтом (`isDefault`); якщо обрана `isComplete=false` → інлайн-warn «реквізити неповні — рахунки/акти заблоковано» (Юр-2) + лінк у адмінку.
- **Договір:** `contractRequired`-toggle (дефолт залежить від моделі — для `fixed` = true). Якщо required і немає `contractDocumentId` → інфо «проєкт активується, але рахунки/акти заблоковано до завантаження підписаного договору» (П3, гейт не блокує активацію). Слот upload / вибір шаблону договору (06-А, гейт документів П3 — повноцінний редактор шаблонів = окремо, тут лише прив'язка).

**Крок 5 — Гейти і terms:**

- `requiresApproval` (02-А, погодження оцінки) — toggle, дефолт компанії.
- `paymentTermsDays` (05-Г) — поле з підписом каскаду (null → дефолт компанії → агенції).

CTA «Створити проєкт» → активація з можливими warn-бейджами (договір/юр-особа). СТАНИ: валідація обов'язкових per-модель (inline-помилки); loading при сабміті; manager — майстер недоступний (фінанси). АДАПТИВ: desktop — степпер 2 колонки (поля + правий саб-превʼю розрахунку); mobile — вертикальний степпер по 1 кроку. ЗВ'ЯЗОК: 05-ПРОЕКТИ §5 (обов'язковість), 06-В, 20-Д, 02-А/В, 05-Г. НОВЕ.

### 2.3. Екран проєкту (НОВИЙ) — задачі, нарахування, маржа

**Маршрут:** `/projects/:id`. ПРИЗНАЧЕННЯ: операційна+фінансова панель одного проєкту.

ВМІСТ:

- **Шапка:** назва · клієнт · модель-pill · валюта · сума · цикл · `nextCycleAt` · юр-особа · warn-бейджі (договір/юр-особа). Дії: Редагувати, **Закрити цикл** (лише для `manual` або як ручний replay — кнопка викликає той самий код закриття з `periodStart/End`, owner задає діапазон), Деактивувати.
- **Задачі (канбан/список)** — РЕЮЗ `workspace-tasks.jsx`: задачі проєкту в звичайному потоці виконавцям. **Zero-billed (`included_in_subscription`)** задачі — позначка-chip «у складі абонплати / не білиться окремо» (НЕ окрема дошка — звичайний канбан, лише візуальний маркер); їхні години → собівартість проєкту.

- **Розріз маржі (22-Д)** `[owner]`: виручка − собівартість = маржа + маржа% + «оплачено N%» (П2). Для абон-проєкту собівартість включає zero-billed години (приклад: $100 − 6год×$12 = $28). Per-виконавець розбивка (TimeLog по `executorId`, у валюті проєкту + USD-конвертація). Manager — весь маржа-блок прихований.

СТАНИ: empty (немає задач/нарахувань) → відповідні плейсхолдери; gate-warn банер (договір/юр-особа); loading → skeleton; manager — без маржі та кнопок генерації нарахувань. АДАПТИВ: desktop — шапка + 2 колонки (задачі ліворуч, нарахування+маржа праворуч); mobile — стек, маржа-блок згортається. ЗВ'ЯЗОК: 05-ПРОЕКТИ (В12 zero-billed, маржа), 06-В (закриття циклу/документи), 22-Д. НОВЕ (реюз канбану з `workspace-tasks.jsx`).

## 3. СТАВКИ / КОМПЕНСАЦІЇ (12 · П1) — РЕЮЗ `workspace-admin.jsx` (`EditMemberModal`) + ДОДАТИ

ВМІСТ (форма ставки виконавця, 12-КОМПЕНСАЦІЇ):

**СТАНИ (для всіх документів).** _draft_ — водяний знак «ЧЕРНЕТКА / DRAFT», номер ще не зафіксовано. _generated/sent_ — фінал, immutable. _signed_ — штамп підпису + audit-рядок. _superseded_ — банер «замінено документом №…» (05-В/immutability). _gate-блок_ — якщо юр-особа агенції `isComplete=false`, генерація заблокована: у Workspace показуємо ворнінг «заповніть реквізити юр-особи», PDF не рендериться (Юр-2).

#### 7-bis. Публічна сторінка рахунку (06-Д · П1) — `НОВЕ`

**ПРИЗНАЧЕННЯ.** Лінк на рахунок **без логіна** (guessable-захист: signed-URL/токен, не послідовний ID — Аудит 06-А access-check). Клієнт відкриває, бачить рахунок і платить.

**ВМІСТ.** Хедер `DocBrand`; рендер рахунку (той самий `wfd-page`, UA або EU за юр-особою); підсумок до сплати великим; **кнопка «Оплатити»** (05-А, ті самі стани лінка, що в Portal-білінгу); блок реквізитів для ручного переказу (IBAN агенції) + QR (наявний `FakeQR` у toolkit); статус-стрічка «надіслано / переглянуто / оплачено» (06-Г). Кнопка «Завантажити PDF».

**СТАНИ.** _valid_ — рахунок + оплата. _paid_ — зелений банер «оплачено, дякуємо». _expired/void_ — «лінк недійсний / рахунок анульовано». _overdue_ — бейдж прострочення + dunning-текст (05-Б). Без логіна — **жодних інших даних клієнта** (лише цей рахунок).

**АДАПТИВ.** Desktop — центрована сторінка-документ (як `wfd-page`). Mobile — рахунок на повну ширину, sticky-кнопка «Оплатити».

**ЗВʼЯЗОК.** 06-Д, 05-А, 06-Г. Реюз `DocBrand` / `FakeQR` / `wfd-page` з `documents-screens.jsx`.
