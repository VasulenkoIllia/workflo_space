# EMAIL-INBOUND — налаштування (власнику)

> **Що це.** Клієнт пише листа на спільну support-скриньку → система сама створює
> тікет у `/support` (або дописує відповідь у наявний тред). Механіка **graceful-off**:
> поки змінні `INBOUND_IMAP_*` не задані — полінг просто **вимкнений**, решта системи
> працює як завжди. Тобто зараз усе зібрано й запушено, а **вмикається воно рівно тоді,
> коли ти виконаєш кроки нижче** (створиш скриньку + додаси env на сервер).
>
> Слайс: **S12-05**. Код: `apps/api/src/services/inboundEmail.ts` (маршрутизація),
> `apps/api/src/cron/inboundEmail.ts` (полер, ~кожні 2 хв). Модуль — [`modules/29-support.md`](modules/29-support.md).

---

## Крок 1 — створити окрему support-скриньку

Заведи **окрему, присвячену лише підтримці** поштову скриньку, напр. `support@workflo.space`.

> ⚠️ **Не давай сюди особисту пошту.** Полер помічає прочитані листи прапорцем `\Seen`
> у цій скриньці — це нормально для сервісного ящика, але ти не хочеш, щоб воно чіпало
> твою робочу пошту. Одна скринька = один потік тікетів.

Де завести — байдуже (хостинг домену, Zoho, Google Workspace, Fastmail…). Головне, щоб
провайдер давав **IMAP-доступ**.

## Крок 2 — увімкнути IMAP і отримати креденшли

- У налаштуваннях скриньки **увімкни IMAP** (у деяких провайдерів він вимкнений за замовч.).
- Дізнайся **IMAP-host і порт** провайдера (майже завжди TLS-порт **993**). Приклади:
  - Google Workspace: `imap.gmail.com:993`
  - Zoho (EU): `imappro.zoho.eu:993`
  - Багато хостингів: `mail.твійдомен:993` або `imap.твійдомен:993`
- **Google Workspace / Gmail:** звичайний пароль не підійде — увімкни 2FA і створи
  **App Password** (пароль застосунку), його й клади в `INBOUND_IMAP_PASSWORD`.

## Крок 3 — додати env на сервер

Змінні кладуться в **той самий `.env`, який читає API/воркер** (за патерном
[`SERVER_UPDATE_2026-07.md`](SERVER_UPDATE_2026-07.md): staging `= /var/www/srv/workflo/staging/.env`,
production `= /var/www/srv/workflo/production/.env`). Оскільки воркери за замовчуванням
крутяться **inline в API-контейнері** (`RUN_WORKERS_INLINE` не `false`) — саме API їх і читає.

```bash
cd /var/www/srv/workflo/production   # або .../staging
cat >> .env <<'ENV'
INBOUND_IMAP_HOST=imap.твійпровайдер
INBOUND_IMAP_USER=support@workflo.space
INBOUND_IMAP_PASSWORD=<пароль-або-app-password>
ENV
```

Три змінні вище — **обовʼязкові** (без будь-якої з них фіча лишається вимкненою).
Решта — з дефолтами, додавай лише якщо треба відхилитись:

| Змінна                  | Дефолт          | Навіщо                                             |
| ----------------------- | --------------- | -------------------------------------------------- |
| `INBOUND_IMAP_HOST`     | — (обовʼязкова) | IMAP-хост провайдера                               |
| `INBOUND_IMAP_USER`     | — (обовʼязкова) | повна адреса скриньки                              |
| `INBOUND_IMAP_PASSWORD` | — (обовʼязкова) | пароль / app-password                              |
| `INBOUND_IMAP_PORT`     | `993`           | порт IMAP                                          |
| `INBOUND_IMAP_SECURE`   | `true`          | TLS. `false` — лише для рідкісного STARTTLS на 143 |
| `INBOUND_IMAP_MAILBOX`  | `INBOX`         | яку теку читати                                    |

## Крок 4 — задеплоїти й перевірити

1. Закоміть/запуш як завжди — деплой підхопить новий `.env` (нові змінні їдуть з compose-манифестом).
2. Після рестарту глянь лог API:
   - **вимкнено** (env не доїхали) → рядок `inboundEmail: INBOUND_IMAP_* не задані — полінг вимкнено`;
   - **увімкнено** → цього рядка нема; за хвилину-дві після старту зʼявляться `inboundEmail: poll complete`
     (лише коли в скриньці були нові листи).
3. **E2E-перевірка:** з пошти **зареєстрованого клієнта** (адреса є в системі й привʼязана до
   компанії) напиши листа на `support@workflo.space` → за ≤2 хв у `/support` має зʼявитися
   тікет з бейджем **📧 email**. Відповідь на цей самий тред (In-Reply-To) дописується
   у той самий тікет і повертає його в статус «open».

## Як воно поводиться (щоб не було сюрпризів)

- **Тікет створюють лише відомі відправники.** Лист від адреси, якої нема в системі (або
  профіль без компанії) — **пропускається** (у лог пише `message skipped reason=unknown_sender`),
  але **помічається прочитаним**, щоб не крутити його щоразу. Оригінал лишається в самій
  скриньці — читай там за потреби.
- **Ідемпотентність.** Кожен лист має унікальний `Message-ID`; повторний полінг того самого
  листа тікет не задублює (унікальний індекс `ticket_messages.sourceMessageId`).
- **Тредінг.** Відповіді (`In-Reply-To`/`References`) підшиваються у наявний тікет, а не
  плодять нові.
- **Тема.** Префікси `Re:`/`Fwd:` зрізаються; порожня тема → «(лист без теми)».
- **Безпека (майте на увазі).** Поле `From` листа технічно можна підробити — тоді в черзі
  зʼявиться тікет «начебто від клієнта X». Привілеїв це не дає (звичайне звернення в чергу),
  але команда має тримати це в голові при чутливих запитах. Дій за листом (зміна доступів,
  реквізити тощо) — лише після звірки каналом, не наосліп.
- **Single-flight.** Повільний IMAP-прохід не накладається на наступний тік; полінг раз на ~2 хв.

## Вимкнути назад

Прибери (або закоментуй) `INBOUND_IMAP_HOST/USER/PASSWORD` у `.env` і передеплой — крон
знову не стартує, тікети з пошти не створюються. Наявні email-тікети лишаються.
